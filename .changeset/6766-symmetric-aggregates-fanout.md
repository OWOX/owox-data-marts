# Correct COUNT DISTINCT, SUM, and AVG across joined Data Marts (fan-out fix)

`COUNT DISTINCT`, `SUM`, and `AVG` metrics on a joined Data Mart are now computed correctly at the report grain, including across multi-hop bridges (a joined Data Mart reached through another joined Data Mart). Previously each was pre-aggregated on the join key and then re-aggregated, which over- or under-counted (`COUNT DISTINCT`), over-summed (`SUM`), or produced an unweighted average-of-averages (`AVG`) whenever the same entity was reachable through more than one path. Each metric is now computed with a dedicated "sleeve" pass that carries the raw identity to the report grain, so each grouped value and the grand total each match their own ground truth. These are symmetric (non-additive) aggregates: an entity reachable under two dimension values is counted once in each group but once overall, so a column's per-group values need not sum to its Totals value — that is correct, not a discrepancy. Applies to BigQuery, Athena, Redshift, Snowflake, and Databricks.

For `SUM`/`AVG`, the value is de-duplicated by the joined field's pre-join group key, or — when the field is a raw passthrough (pre-join `ANY_VALUE`) — by a per-row surrogate numbered within that key. A declared primary key on the joined Data Mart is not consulted in either case (planned follow-up). This is correct for well-formed data (rows that are true duplicates, with no key to tell them apart, are legitimately counted as distinct). `MIN`, `MAX`, and `COUNT` on joined Data Marts are unchanged; the main-side Unique Count (by primary key) is unchanged. Joined percentile metrics still return an unweighted approximation — they are not yet sleeve-routed.

A joined `COUNT DISTINCT` on a field that already has a non-identity pre-join roll-up (e.g. a text field pre-aggregated with `STRING_AGG` before the join) now counts distinct raw values at the report grain, not distinct rolled-up values. This is more correct — the previous behavior counted distinct rolled-up values, an approximation that could conflate different raw values that happened to roll up into the same combined result — but the number can change for a saved report using such a field.

Known limitation: a metric (`HAVING`) filter on a joined `COUNT DISTINCT`, `SUM`, or `AVG` is not yet supported and is rejected with a clear error — filter on a main-side column or a different metric instead. A previously-saved report carrying such a filter will be rejected with that error on its next run. Output-controls validation errors now reach the interface with their details (the column and what to change) instead of only a generic "validation failed" line, which is what makes that error actionable.

Totals now honour metric (`HAVING`) filters. A Totals row has no grouping, so a per-group constraint cannot apply to it directly — it used to be dropped, and Totals then summarised rows the report itself hides. Totals are now computed over the rows of the groups that pass the filter. They stay symmetric while doing so: an entity reachable from two surviving groups is still counted once by `COUNT DISTINCT`, and a joined row that fans out to several groups is still summed once. **Totals will change for any saved report that carries a metric filter** — they were previously computed over hidden groups as well.

For a JOINED field, Totals no longer offer `COUNT` alongside `COUNT DISTINCT`. The two are computed at different grains — `COUNT DISTINCT` reads the raw path before the join's fan-out is collapsed, `COUNT` counts the rows that survive it — so shown side by side they can invert `COUNT DISTINCT <= COUNT`, an expectation both people and AI callers rely on. Nobody asked for that `COUNT`: Totals add every allowed function themselves. A non-joined (main) field is unchanged and still shows both.

A relationship whose join is incomplete or unusable is now rejected with an explanation instead of failing at the warehouse. That covers a relationship saved with no join conditions (a supported draft state — it is refused when a report tries to USE it, not when you save it), and one joining on a nested field such as `address.city`, which the query engine cannot express and which was previously accepted and then failed with a raw database error. Editing a relationship no longer requires filling in the join conditions, matching what creating one already allowed.

Reading a Redshift report now fails with an explanation rather than wrong data when two report columns cannot be told apart — Redshift lower-cases and truncates long identifiers, so two columns differing only in case, or only past 127 bytes, arrive as one. Such a pair is now rejected when the report is saved, on every warehouse, so the report cannot reach that state in the first place.

Totals that cannot be computed are now reported instead of silently omitted. They are still best-effort — a failure never costs the query its rows — but an empty Totals block used to be indistinguishable from a report that has no totals at all, which invites summing the returned rows instead (wrong for any non-additive metric). The reason now travels with the response and is recorded in Run History.

The internal names these passes use are now reserved: a joined Data Mart with a source column named `__owox_rid`, or a report that groups by a field (or output alias) named `_oid`/`_oid_<n>`, `_oid_key_<n>`, `_val`/`_val_<n>`, or `_dedup` alongside a joined `SUM`/`AVG` metric, is rejected with an error naming the column instead of silently returning a corrupted value — rename the field or its alias. The Totals restriction adds `_kept_groups` and `_owox_kg_<n>` to that reserved set.
