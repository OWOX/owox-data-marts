# Correct COUNT DISTINCT, SUM, AVG, percentiles, and Combined across joined Data Marts (fan-out fix)

`COUNT DISTINCT`, `SUM`, `AVG`, the percentile metrics (`P25`, `Median`, `P75`, `P95`), and `Combined` on a joined Data Mart are now computed correctly at the report grain, including across multi-hop bridges (a joined Data Mart reached through another joined Data Mart). Previously each was pre-aggregated on the join key and then re-aggregated, which over- or under-counted (`COUNT DISTINCT`), over-summed (`SUM`), produced an unweighted average-of-averages (`AVG`), weighted a percentile by how many times the join repeated each value, or repeated the same text in `Combined` once per matching row, whenever the same entity was reachable through more than one path. Each metric is now computed with a dedicated "sleeve" pass that carries the raw identity to the report grain, so each grouped value and the grand total each match their own ground truth. These are symmetric (non-additive) aggregates: an entity reachable under two dimension values is counted once in each group but once overall, so a column's per-group values need not sum to its Totals value — that is correct, not a discrepancy. Applies to BigQuery, Athena, Redshift, Snowflake, and Databricks. **Numbers will change for any saved report using one of these metrics on a joined Data Mart whose join fans out.**

For `SUM`, `AVG`, and the percentiles, the value is de-duplicated by the joined field's pre-join group key, or — when the field is a raw passthrough (pre-join `ANY_VALUE`) — by the joined Data Mart's own declared primary key. Two rows agreeing on that key and on the value are the same row the join returned twice and are counted once; two rows agreeing on the key but not on the value stay separate, so contradictory data is never silently resolved to one of its versions. A joined Data Mart with no declared primary key falls back to a per-row surrogate, which cannot tell a genuine duplicate row from two distinct ones — declaring a key is what makes duplicates collapse. As elsewhere, a declared key is trusted: a key that is not in fact unique will merge rows — and so will one whose column is empty on more than one row, since empty values are indistinguishable. Declare a key only on a column that is genuinely unique and always filled. `MIN` and `MAX` on a joined Data Mart are computed the same way, over the same rows. They used to read the value the pre-join roll-up had already collapsed, which measured a different set from `AVG` on the very same column and could leave `MIN` above the average. `COUNT` is the one metric left unchanged, deliberately: it counts the rows that survive the join, which is a different question rather than a distorted one. The main-side Unique Count (by primary key) is unchanged.

For a JOINED field, `COUNT` and `COUNT DISTINCT` are no longer shown side by side. The two are computed at different grains, so together they can invert `COUNT DISTINCT <= COUNT`. **A report that selects both on a joined field now shows only `COUNT DISTINCT`** — the report is not rejected, and `COUNT` on its own keeps working exactly as before. Totals stop offering the pair for the same reason. A non-joined field is unaffected.

A joined field whose pre-join roll-up is "any value" is now rolled up deterministically. That roll-up is read twice — once for the report's own grouping and again inside the fan-out correction — and an engine free to evaluate the two separately could return different values, which made the correction silently produce empty results. Applies to text, number, date and time fields; other types are unchanged.

A joined `COUNT DISTINCT` on a field that already has a non-identity pre-join roll-up (e.g. a text field pre-aggregated with `STRING_AGG` before the join) now counts distinct raw values at the report grain, not distinct rolled-up values. This is more correct — the previous behavior counted distinct rolled-up values, an approximation that could conflate different raw values that happened to roll up into the same combined result — but the number can change for a saved report using such a field.

Known limitation: a metric (`HAVING`) filter on any of these joined metrics — `COUNT DISTINCT`, `SUM`, `AVG`, `MIN`, `MAX`, `Combined`, or a percentile — is not yet supported and is rejected with a clear error — filter on a main-side column or a different metric instead. A previously-saved report carrying such a filter will be rejected with that error on its next run. Output-controls validation errors now reach the interface with their details (the column and what to change) instead of only a generic "validation failed" line, which is what makes that error actionable.

Rejected requests now say what was actually wrong with them. Every failed validation rule — across the whole API, not only reports — reached the caller as the single word "Bad Request Exception", with each per-field reason dropped before the response left the server. Each reason now travels with the response and is shown in the interface.

Totals now honour metric (`HAVING`) filters. A Totals row has no grouping, so a per-group constraint cannot apply to it directly — it used to be dropped, and Totals then summarised rows the report itself hides. Totals are now computed over the rows of the groups that pass the filter. They stay symmetric while doing so: an entity reachable from two surviving groups is still counted once by `COUNT DISTINCT`, and a joined row that fans out to several groups is still summed once. **Totals will change for any saved report that carries a metric filter** — they were previously computed over hidden groups as well.

For a JOINED field, Totals no longer offer `COUNT` alongside `COUNT DISTINCT`. The two are computed at different grains — `COUNT DISTINCT` reads the raw path before the join's fan-out is collapsed, `COUNT` counts the rows that survive it — so shown side by side they can invert `COUNT DISTINCT <= COUNT`, an expectation both people and AI callers rely on. Nobody asked for that `COUNT`: Totals add every allowed function themselves. A non-joined (main) field is unchanged and still shows both.

A relationship whose join is incomplete or unusable is now rejected with an explanation instead of failing at the warehouse. That covers a relationship saved with no join conditions (a supported draft state — it is refused when a report tries to USE it, not when you save it), and one joining on a nested field such as `address.city`, which the query engine cannot express and which was previously accepted and then failed with a raw database error. Editing a relationship no longer requires filling in the join conditions, matching what creating one already allowed.

Reading a Redshift report now fails with an explanation rather than wrong data when two report columns cannot be told apart — Redshift lower-cases and truncates long identifiers, so two columns differing only in case, or only past 127 bytes, arrive as one. Such a pair is now rejected when the report is saved, on every warehouse, so a new report cannot reach that state. **An already-saved report carrying such a pair is rejected on its next run** — on Redshift it was returning data from the wrong column.

Totals that cannot be computed are now reported instead of silently omitted. They are still best-effort — a failure never costs the query its rows — but an empty Totals block used to be indistinguishable from a report that has no totals at all, which invites summing the returned rows instead (wrong for any non-additive metric). The reason travels with the response and is recorded in Run History; AI callers are told only that totals failed, since a warehouse message quotes the query and its table and column names.

The internal names these passes use are now reserved: a joined Data Mart with a source column named `__owox_rid`, or a report that groups by a field (or output alias) named `_oid`/`_oid_<n>`, `_oid_key_<n>`, `_val`/`_val_<n>`, or `_dedup` alongside a joined `SUM`/`AVG`/percentile metric, is rejected with an error naming the column instead of silently returning a corrupted value — rename the field or its alias.

A server error now shows a message identifying the request instead of failing silently.
